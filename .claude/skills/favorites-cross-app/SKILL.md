# favorites-cross-app

The second favorites channel: one shared, app-neutral list synced with other Podcasting 2.0 apps. The per-item kind 30001 events are a separate channel — see the `favorites` skill.

## Tests for this subsystem

```
npx tsx --test lib/nostr/shared-favorites.test.ts        # merge, wire round trip (mirror of BMB’s check:favsync)
npx tsx --test lib/nostr/shared-favorites.relay.test.ts  # the relay read, against scripted misbehaving relays (~10s)
npx tsx lib/nostr/shared-favorites.relay-probe.ts        # read-only smoke check against the REAL default relays (network; not in --test runs)
npx tsx scripts/backup-favorites.ts dump > fav.json      # snapshot favorites before enabling SHARED_FAVORITES_APPLY_DELETES
```

## Cross-app favorites — the shared kind:30078 list
Favorites sync with **Boost Me Bitch** (and any other app implementing the format) through ONE NIP-78 application-data event at `d:podcast:favorites`, items as NIP-73 `podcast:guid:` / `podcast:item:guid:` identifiers. Full spec: [`PC20-Nostr/specs/pc20-favorites.md`](https://github.com/ChadFarrow/PC20-Nostr/blob/main/specs/pc20-favorites.md) — the canonical, app-neutral copy, kept outside both implementing repos so there is exactly one of it. (`docs/pc20-favorites.md` here is now a stub pointing at it.) **That document, not this code, is what a third app implements against.** Files: `lib/nostr/shared-favorites.ts` (pure format + merge + relay read), `lib/nostr/shared-favorites-client.ts` (baseline storage, DB→wire mapping, debounce), `app/api/favorites/sync-shared/route.ts` (inbound reconcile).

**This is a SECOND channel. The per-item kind 30001 events are untouched** — the Community tab reads those, and its author-scoped filters and d-tag ladder are tuned against real prod data. Don't collapse the two.

**The whole feature is behind a pubkey allowlist while it's being trialled** — and it is **not off by default**: `SHARED_FAVORITES_ALLOWLIST` in `shared-favorites-client.ts` is a hard-coded array that currently holds Chad's npub, unioned with `NEXT_PUBLIC_SHARED_FAVORITES_PUBKEYS` (comma-separated, **npub or hex** — `normalizePubkey` accepts both). Empty array *and* unset env means entirely off. `sharedFavoritesEnabledFor()` short-circuits `syncSharedFavoritesNow`, `requestSharedFavoritesSync` and `pullSharedFavorites` (the last returns `status:'off'`), so a signed-in user costs no relay read, no publish, no reconcile, nothing on any page load. It exists because **this repo has no preview environment** — `git push origin main` *is* the production deploy — and `NostrContext`'s pull effect fires for every signed-in user, so shipping it ungated would publish everyone's favorites to a public `podcast:favorites` list they never asked for. Their favorites are already public via the per-item kind 30001 events, so it's not a new disclosure in kind, but a new aggregated artifact under someone else's key is not a side effect a test gets to have. **`NEXT_PUBLIC_` means it bakes at build time** — set it *before* the deploy that should use it, and redeploy to change it. **This gate is scaffolding: deleting `sharedFavoritesEnabledFor` and its three call sites is what "ship to everyone" means.**

**The disclosure prerequisite is now MET** (`components/favorites/SharedFavoritesDisclosure.tsx`, on `/favorites` beside the sync control). Turning the sync on for everyone creates a **new aggregated public artifact** — one `podcast:favorites` list per user, under their own key. Their favorites are already public via the per-item kind 30001 events, so it is not a new disclosure *in kind*, but it is a new object they did not ask for, and the [spec](https://github.com/ChadFarrow/PC20-Nostr/blob/main/specs/pc20-favorites.md) §"On `content` being plaintext" ("Say so in your UI") tells implementers to say so. That notice now exists, so removing the gate is a decision rather than a silent disclosure change. **Two states render nothing on purpose, and keeping them that way is what makes it a disclosure rather than a lie**: signed out (no key, nothing published) and a `nip05` read-only session (no signer, so nothing is ever signed or sent). The cross-app sentence is gated separately on the allowlist — a non-trial user's per-item events are public, but no `podcast:favorites` list exists under their key. It is deliberately **not dismissible**. Verify with the puppeteer recipe across all four states; the two render-nothing cases are the ones worth testing.

Still worth having from the trial before removing the gate: whether the degraded notice ever fires falsely, whether the first-run push (it carries the user's entire library) lands, whether duplicate `FavoriteAlbum` rows appear, and whether an unfavorite in the other app really propagates here.

- **NIP-78 app data, deliberately NOT NIP-51's kind:30003 (bookmark sets).** Kind 30003 is user-named bookmark collections — saved links. Podcast favorites belong in neither that category nor that write-space: a generic bookmark client that lets someone edit a set would rewrite this list with none of the discipline below, and it would be doing nothing wrong. The trade is that favorites are no longer visible in generic NIP-51 list clients, which is intended. `content` stays empty and public, unlike `nwc-backup.ts`, which NIP-44 encrypts its 30078 payload — a second app has to be able to read this one.
- **A blind publish deletes another app's favorites.** kind:30078 is replaceable and this address has many writers, so every publish replaces the whole event — silently, on someone else's device, with no undo. The only exported writer is `syncSharedFavorites`, which reads → merges → publishes as one step; there is deliberately no "publish my list" function for a caller to reach for.
- **The merge diffs against a BASELINE, not the local set.** `localStorage['sk_shared_favorites_baseline:<pubkey>']` holds the id list this device last agreed with the relay on. `next = (latest ∪ (local − baseline)) − (baseline − local)`. Publishing the local set alone erases every entry another app added; publishing the union alone makes unfavoriting impossible, permanently. An empty local set with an empty baseline must delete nothing; with a full baseline it's a real clear-all. Both pinned in `shared-favorites.test.ts`.
- **A degraded read is reported, not just handled** (`SharedSyncStatus` in `shared-favorites-client.ts`, rendered by `components/favorites/SharedFavoritesNotice.tsx` under the Sync control on `/favorites`). The guard below is correct and was silent, and silence costs more than it looks: a degraded read and an empty list render identically, so the correct behaviour looks exactly like data loss — in the sibling app that produced half an hour of production debugging and a near-revert of a correct commit. **Reads and writes are SURFACED as one flag but TRACKED as two** (`setSyncHealth('read'|'write', …)`): a favorite toggled while the relays are unreachable skips its publish and otherwise looks exactly like one that synced, so both halves belong in the same notice — but the push runs on *every* toggle, so one shared flag let a successful **write** clear a `degraded` raised by a failed **read**. The notice then vanished the next time the user favorited anything while inbound reconcile was still broken, taking the Retry button — the only thing that re-runs the pull — with it. Reporting success is worse than staying silent. They fail independently and must clear independently.

- `'off'` (not in the allowlist) and signed-out both render nothing — there is no sync to fail, and claiming a relay problem would be a lie.
- The pull is **single-flight, keyed on pubkey**. Unkeyed, an account switch without a reload joins the previous user's run and resolves with their result. The retry button is what makes concurrent pulls reachable at all.
- **Every exit path must settle the status**, including a throw. `fetchSharedFavorites` opens with a dynamic `import('nostr-tools/pool')` that rejects offline — exactly the population the notice exists for — and an unhandled rejection left the flag pinned at `'syncing'`, which renders as nothing.
- **The status-cache invalidation is dispatched BEFORE the push, not after.** The push can throw, and an enclosing catch then swallowed the dispatch even though the reconcile had already written rows — leaving stale hearts, i.e. issue #190 again via the writer that dispatch exists for. Order it against what has happened, not what is still to come.
- **A degraded read publishes nothing, and reconciles nothing.** `trustworthy:false` aborts at the client AND is rejected by the route — locked at both ends, because the failure mode is deleting favorites the user still has.
- **`trustworthy` cannot be built on `pool.subscribeMany`'s aggregate `oneose`** — that was a bug for the feature's whole life, found only once `shared-favorites.relay.test.ts` existed to script a misbehaving relay. Two different non-answers are folded into that callback and **both reported as an answered read**: (1) `AbstractRelay.baseEoseTimeout` (4400ms) **synthesizes** an EOSE on a timer when a relay never sends one — under the 5s default, so a relay that accepted the socket then said nothing read as `trustworthy` (measured, 4424ms); (2) a **failed connection** also counts toward the aggregate, so an offline device reported `trustworthy` in **19ms**. Either one means an empty read is believed, `local` is merged onto nothing, and the republished list is stripped of every entry another app contributed. So the read now subscribes **per relay**: a relay has answered only if it connected *and* sent a real EOSE inside the window, and the bar is `reached > 0 && answered === reached` — every relay we could actually reach said "I have nothing". `eoseTimeout` is set just past our own deadline (**a large value leaves a real timer pending long after the read returns** — 110s of dangling timer, which is also why the harness took 114s), and `CONNECT_TIMEOUT_MS` (2s) is capped well under the overall budget because **one dead relay sized to the full remaining budget burns the entire window** — `wss://nostr.oxtr.dev` did exactly that, turning every read into 5s. Both were fixed: the cap took it to ~2s and **dropping that relay from `getDefaultRelays()` took it to ~820ms** on a real 318-item list. `nostr.oxtr.dev` is gone (2026-08-12; DNS resolved, nothing accepted a connection, 3/3 timeouts at 8s). That is the **second** dead default after `relay.nsec.app` — nothing prunes them automatically, so **check a relay before adding one**: connect, send a REQ, require a real EOSE. `lib/nostr/shared-favorites.relay-probe.ts` does exactly that against the live list and is the fastest way to spot the next one.
- **A relay that is merely unreachable drops out of the denominator; one that hangs makes the read degraded.** That asymmetry is deliberate: the default list ships a dead relay, so counting unreachable relays against the read would leave the feature permanently degraded, while a hung relay genuinely is an unknown. Skipping a publish is retried on the next toggle; clobbering another app's favorites is not recoverable.
- **Reconciliation ships with deletes OFF.** It is the only destructive write in the sync, and `FavoriteAlbum`/`FavoriteTrack` rows are the only copy — Boost Me Bitch can rebuild its entire list from the shared event, these cannot. Set `SHARED_FAVORITES_APPLY_DELETES=true` to enable. Until then the reconcile still runs and reports `wouldRemove` in the response and the log, so you can watch it be right before it is allowed to be wrong. **Snapshot first**: `railway run --service StableKraft --environment production npx tsx scripts/backup-favorites.ts dump > favorites-$(date +%F).json`, restored with `restore <file>` (additive and idempotent).
- **Minting `Feed` rows from another app's list is OFF too** (`SHARED_FAVORITES_IMPORT_UNKNOWN=true` to enable). BMB is a general podcast app and this one is music, so a shared list carries talk podcasts — and importing them writes rows into a catalogue with whole subsystems (the blacklist, `medium=podcast` detection, `fix-podcast-types`) devoted to keeping non-music out. With it off, `addUnresolvedFeeds` is skipped but the guids still come back as `unresolvedFeedGuids` in the response, which is how you see what a real list actually contains before deciding whether any of it belongs here.
- **And a sanity cap that applies even when deletes are on.** A single pass refuses to remove more than `max(5, 50%)` of the eligible rows, logs `🛑`, and removes nothing. A mass removal arriving here means another app dropped a large share of the entries *this* app also holds — plausible as a bug, implausible as a user action, since the two apps' favorites barely overlap. A real clear-all still applies once the remaining set is under the cap.
- **The inbound reconcile's ADD loops must match every id format too** (`sync-shared/route.ts`). The polymorphism above applies here as much as to the read paths: the album loop matched only `Feed.id` while the track loop beside it checked both forms, so a favorite already stored under `Feed.guid` found no match and a **second row** was created keyed by the id — which `@@unique([userId, feedId])` cannot reject, because the strings differ. The album then rendered **twice** in `/favorites` and was reported as newly arrived on every first pull. Keep the two loops symmetric; an asymmetry between them is exactly how this hid.
- **Reconciliation deletes only what could have been on the wire.** A row is eligible only if it is `userId`-scoped (never `sessionId`), its type is album/track (publishers and playlists are StableKraft-local constructs with synthetic ids — out of scope both directions), and it resolves to a non-null `Feed.guid`/`Track.guid`. **Something that can never appear on the list can never be missing from it**, so a guid-less favorite is never touched — that's the guard against a null-guid feed silently unfavoriting itself.
- **`k` tags come from a known-kind table, never string-scanning.** `Track.guid` is routinely a permalink URL, so "everything before the last colon" yields `podcast:item:guid:https` — a tag no relay filter matches, breaking discovery with nothing visibly wrong. Pinned by a test.
- **Identifiers we can't resolve still ride along.** `partitionSharedFavorites` is lossy on purpose and runs at resolution time only; the merge never looks inside an `i` tag. BMB's episode favorites, a third app's `podcast:publisher:guid:`, unrecognized tags, and `k` tags for kinds we don't generate all survive our republish.
- **Unfavorite fires the shared sync outside the `nostrEventId` guard** (`FavoriteButton`). A kind-5 needs the id of the event it deletes, so a favorite whose 30001 publish once failed can never be unfavorited on that channel — the shared list has no such dependency, removal being just absence from the next revision.
- `favorite-item-lookup.ts` gained a **4th rung, `Feed.guid`, deliberately LAST**: the first three are backed by measured prod data (7 / 41 / 69 of 121 d-tags) and reordering would change which row an existing tag resolves to.
- **Both relay harnesses need a `WebSocket` global that Node 20 does not have**, and this repo targets Node 20 (`.nvmrc`, `node:20-alpine`) — the default global only arrived in Node 21. `nostr-tools` captures it once at module load, so `installNodeWebSocket()` (`lib/nostr/node-websocket.ts`, called from both) supplies `ws` instead. **It patches three places and all three are load-bearing**: the global, plus `useWebSocketImplementation` on **both** the CJS and ESM copies of `nostr-tools/pool` — this repo is CommonJS, so a *static* import of that package resolves the CJS build while `fetchSharedFavorites`'s *dynamic* `await import()` resolves the ESM build, two module instances with two `_WebSocket` variables. Patching one leaves the other silently broken. **The symptom points nowhere near the cause**: the relay test's degraded-read cases keep passing (a failed connection is indistinguishable from the degradation they assert) while only the seven "a relay answers" cases fail, and the probe reports **every** default relay dead — a tool for finding dead relays declaring all of them dead. Reproduce on a newer Node with `NODE_OPTIONS=--no-experimental-websocket`, which is the only way to see this without CI. (This is also why the helper aliases the import: eslint reads any `useFoo()` call as a React hook and `next lint` errors, not warns.)
- Tests: `npx tsx --test lib/nostr/shared-favorites.test.ts`. The same vectors are pinned on the BMB side by `npm run check:favsync` — **change one, change both**, or the two implementations drift apart on a list they share.
